# Loupe

個人用Androidギャラリーの試作です。
Android 11以降を対象に、Android 16のLeitzphoneへインストールして表示を確認しました。

## 実装済み

- RAW 51拡張子とJPEGの一覧表示（埋め込みJPEGがあるファイルを表示）。撮影日時が取得できる場合は撮影日時、ない場合は更新日時で並べます。
- RAW内のJPEG構造を探索・検証し、最大画素数の画像を抽出して表示します。RAW現像はしません。
- カメラの保存先による絞り込み、写真の拡大、前後の移動。
- 写真へのアクセス許可と、任意のRAWフォルダへの読み取り許可。
- 共有先の登録、並べ替え、プレビューJPEGまたは原本の指定。
- Amazonの日本向け画面でのログインと、写真一覧の読み取り専用の接続診断。
- 既存原本の検索と、ダウンロードした原本のSHA-256照合。
- 確認画面を経た原本１枚のアップロードと復元検証（OM-1 Mark IIの１枚で実機確認済み）。

## 自動同期と容量整理

「クラウド」から「自動同期・端末容量の設定」を開き、フォルダを選ばずに対象を自動検出します。
対象は、指定した機種のRAWと、ダウンロード画像を含むアクセス可能なすべてのJPEGです。
自動整理にはAndroidの「すべてのファイルへのアクセス」を許可します。
加工されていない原本の読み取りを要求し、取得できない場合は同期・整理を止めます。
すべてのファイルへのアクセスを許可しない場合は、位置情報を含めた原本読み取りの許可も必要です。
対象件数と容量を確認してから自動同期を有効にします。
同期はモバイル通信でも動き、Androidの定期処理を使います。省電力設定などで実行が遅れる場合があります。
一度の処理は最大20枚とし、中断後は記録から続けます。
保存結果が不明な原本は自動再送せず、クラウドの検索と復元照合で確認します。

自動整理は同期とは別に有効化します。
初期の保持期間は基準日から７日間です。
JPEGの基準日は撮影日、Androidへのファイル追加日、取得できる作成日の順に選びます。
すべての日付を取得できないJPEGは、復元照合とプレビュー保存を完了するとすぐに整理対象になります。
作成日は変更日時で代用しません。Androidの保存先が実際の作成日を公開しない場合は取得不能として扱います。
撮影日が不明なRAW、整理の権限がない写真、復元照合に失敗した原本は整理しません。
整理直前にクラウドから再取得してSHA-256を照合し、プレビューと管理記録を永続保存し、端末原本も再確認します。
端末から整理した写真も一覧に残り、開くと原本を必要に応じて取得し、高画質表示へ切り替えます。共有にも原本を使います。
クラウドの原本を削除する処理はありません。

自動同期と自動整理は初期状態では無効です。
検証用RAWコピーとJPEGコピーで、クラウド照合後の自動整理とプレビュー保持、元の写真の不変を実機で確認しました。
利用者の原本は削除していません。長時間のバックグラウンド動作は未検証です。
アプリをアンインストールすると端末のプレビューと管理記録が消えます。クラウドの原本はAmazon Photosで閲覧できます。

## 検証したRAW

実ファイル８枚について、抽出したJPEGがExifToolの出力と完全に一致しました。

| 機種 | 枚数 | JPEGの画素数 |
| --- | ---: | --- |
| GR IV | 1 | 6192 × 4128 |
| GR IV Monochrome | 1 | 6192 × 4128 |
| OM-1 Mark II | 2 | 3200 × 2400 |
| E-P7 | 2 | 3200 × 2400 |
| Leitzphone powered by Xiaomi | 2 | 4080 × 3072 |

すべての撮影モードに対応したという意味ではありません。
JPEGにはRAWの回転情報を一度だけ適用します。
RAWの埋め込みJPEGは画素を再圧縮せず、共有用コピーに回転情報を付与します。
ローカルの小サイズプレビューはWebP形式、長辺1280画素以下、品質80です。
原本を開くときは先にプレビューを表示し、取得した原本に切り替えます。RAWの高画質表示は原本に埋め込まれたJPEGを使います。
JPEG原本の共有は元のJPEGをそのまま渡し、RAWをJPEG形式で共有するときは取得した原本から埋め込みJPEGを抽出します。
通信できないときは取得済み原本があればそれを使い、なければ小サイズプレビューを残して取得失敗を表示します。
原本の一時保存は合計512 MiB以下です。次の原本取得時に、24時間以上前のものや容量を超える古い原本を整理します。
この一時保存は、原本整理後も必ず残すプレビューとは別です。
アプリで見えるカメラ別の分類はフォルダ名によるものです。画像を開くとRAWに記録されたモデル名を表示します。

## データの扱い

通常の閲覧では原本を読み取り専用で扱います。自動整理は指定機種のRAWとすべてのJPEGを対象とし、Androidの権限とアプリ内の有効化が必要です。
閲覧用キャッシュは256 MiBを上限として古いものから整理します。
整理した原本の代わりに残すプレビューは、消去可能なキャッシュとは別に永続保存します。
共有用コピーは24時間以上経過したものを、次の共有の準備時に整理します。
端末の原本と共有用コピーは別の領域にあります。

共有先アプリは実際に共有ボタンを押したときだけ開きます。
受け渡すファイルへの読み取り許可だけを渡します。

Amazonのログイン情報はこのアプリのWebViewで扱い、ログや成果物へ書き出しません。
他のアプリのログイン情報は取得しません。
バックアップと端末移行からアプリデータを除外します。
接続診断は日本向けの固定URLに対するGETで、認証情報つきの転送は追従しません。
接続先の参考資料は `docs/cloud-research.md` に記載しています。

## ビルド

JDK 17、Android SDK Platform 35、Build Tools 35.0.0を用意してください。
SDKの場所を `ANDROID_HOME` に設定するか、ローカルだけの `local.properties` に記載します。

```sh
./gradlew assembleDebug lintDebug
```

APKは `app/build/outputs/apk/debug/app-debug.apk` に出力されます。
この試作では開発用署名を使っています。継続運用と更新に使う署名鍵は別途決定します。

抽出処理の検証はJDK 17と実ファイルを使います。
第１引数はRAWフォルダ、第２引数はExifToolで抽出したJPEGフォルダです。
比較用JPEGはRAWの拡張子だけを `.jpg` に置き換えた名前にしてください。
GR IVは `SubIFD1:PreviewImage`、Leitzphoneは `SubIFD:PreviewImage`、OMの２機種は `Olympus:PreviewImage` を使います。

```sh
./tests/run.sh /path/to/raw-samples /path/to/reference-jpegs
```

個人のRAWと写真はソース一式に含めません。

## 連写のまとめ表示

v0.6.0では、同じ機種・保存先・形式の写真について、隣り合う撮影時刻の差が１秒以内なら一覧でひとつにまとめます。
代表画像に枚数を表示し、押すと束の中の写真を選べます。詳細画面の前後移動も、その束の範囲内になります。
「連写のまとめ方」から、まとめ表示なし・１秒・２秒・３秒を選べます。
撮影時刻または機種が不明な写真はまとめません。追加日や更新日時で連写を推測しません。
RAWとJPEG、保存先が異なる写真は別の束です。カメラが記録した連写フラグではなく、時刻差による判定なので、短い間隔の単写も含む場合があります。
ファイルの結合・削除はせず、同期と容量整理は１枚ずつ行います。

実機では30,727枚が12,468枠にまとまり、４枚の束の展開、原本表示、束内の次の写真への移動を確認しました。判定の単体検査８件とビルド・静的検査も成功しました。

## v0.14.0の複数選択とベストショット

写真または連写の枠を長押しすると選択が始まり、タップで追加・解除できます。
下部の「ベストショットだけを操作する」は、選択を始めるたびにオンになります。
オンでは選んだ写真のうち各連写の１位だけを共有し、同率１位はすべて対象にします。単写真も対象です。
連写の枠を選ぶと連写全体を選択します。連写内で個別に選んだ場合、選んでいない写真を共有対象に追加することはありません。
オフでは選んだ写真すべてを共有します。選択した項目数と実際の対象枚数は別に表示します。

順位が未確定の連写を含むと、共有前にダイアログを表示します。
「順位を付ける」でその場から比較を始め、「選択へ戻る」で選択状態を保ったまま戻れます。
未確定が複数組ある場合は、１組ずつ順位を付けられます。確定済みの写真があれば「確定分だけ共有」も選べます。
比較中の「＝」は同順位です。結果は１位、１位、３位のように表示します。

複数画像を共有する際も、原本または原本のJPEGを準備します。共有先アプリ側が複数画像と選択した形式に対応している必要があります。
共有先を開く前に対象を固定し、準備に失敗した場合は一部だけを共有しません。

## 写真追加の反映改善

画面を開いている間のMediaStore変更通知は、最初の通知から約300ミリ秒で索引更新を要求します。
連続取り込みでも待ち時間を延長せず、更新中の追加通知は次の更新へまとめて引き継ぎます。
内蔵ストレージに加え、接続中の外部ストレージの変更世代も確認します。
300ミリ秒は更新開始の待ち時間で、全写真の走査・連写情報の解析が終わるまでの時間は別途かかります。
アプリを閉じている間の定期更新間隔と、Android側で写真がMediaStoreへ登録されるまでの時間は変わりません。

回帰テスト: `sh tests/index-refresh.sh`。更新中の連続通知、強制更新の優先、失敗後の保留要求の引き継ぎを検査します。

2026年10月25日、Leitzphoneへ修正版をデータ保持で更新インストールしました。
専用JPEG１枚はメディアスキャン要求から約2.5秒で索引に入り、アルバム画面への自動表示も確認しました。
続けて10枚を連続追加し、最後のスキャン要求から約2.5秒で全11枚が索引に入り、開いている写真一覧にも「11枚 · 11枠」と表示されました。
これらは小さな検証用JPEGでの測定です。カメラ撮影そのもの、大量RAW取り込み、外部ストレージでの反映時間は未測定です。
検証用画像11枚と専用フォルダは削除しました。

## 手動タグ付け（Issue #1 開発版）

写真一覧または写真詳細の「タグ」からタグを作成し、現在のアルバム・カメラ絞り込み内の端末写真を確認できます。左スワイプはパス、右は付与。「該当しない」「判断を取り消す」「一つ戻す」も画面に表示します。付与済み・除外済みの写真を見直せます。

タグと判断は一覧索引と別のDBに保存します。RAW・JPEG・別保存先のコピーは別写真として扱い、移動先への自動引き継ぎは行いません。原本やEXIF、連写順位、共有選択は変更しません。「自動でタグを広げる」で、付与済み写真を見本に端末内の画像特徴から候補を提示します。付与・除外で次の候補を再計算し、パスはその回だけ保留します。現在は、以下の自動付与にも対応しています。

契約・制限・検証結果は[手動タグ付けの開発記録](docs/tag-judgment-contract.md)を参照してください。

判断モデルの検証: `sh tests/tag-judgments.sh`。端末での保存テストはテストAPKを導入後、`adb shell am instrument -w -e mode tags jp.nano.rawgallery.test/jp.nano.rawgallery.ArchiveInstrumentation`。専用一時DBと架空の写真参照だけを使用します。

テストAPKのIDは`jp.nano.rawgallery.test`に明示固定しています。テスト種類は同じAPKの`mode`引数で切り替えます。更新は同じ署名鍵で`adb install -r`を使い、テストごとにアンインストールしたり別IDを生成したりしません。APKが変更されていなければ再インストールせず、instrumentationだけを再実行できます。端末側のインストール確認が省略されるかは、このID固定だけでは保証しません。

## 見本から関連写真を探す

タグを開き「自動でタグを広げる」を選びます。見本がない場合は「見本の写真にタグを付ける」で一枚付けると自動付与へ進みます。「すべての未判断写真を順に確認」は従来どおり順番に確認する操作です。

- 現在のアルバム・カメラ範囲が対象です。全体を探す場合は「すべての写真」からタグを開きます。
- 初回は画像特徴を端末内で解析し、最初の32枚（小さい範囲は全枚数）から候補を表示します。残りは確認中に解析します。終了・バックグラウンド移行で解析を止め、次回は保存済み特徴を再利用します。
- 複数の付与例それぞれに近い写真を探し、除外例に近い写真は順位を下げます。5枚に1枚は見本から遠い候補も提示します。候補は正解や自動付与の予告ではありません。
- MobileNetV3 smallを同梱しています。写真送信はありません。特徴は1枚1024バイト＋DB管理領域、モデルは約4.1MBです。RAW原本の読込み・プレビュー生成時間は別途かかります。

契約と実測は[関連候補の開発記録](docs/related-tag-contract.md)。単体検証は`sh tests/related-photos.sh`、実機推論検証は固定IDのテストAPKで`adb shell am instrument -w -e mode related jp.nano.rawgallery.test/jp.nano.rawgallery.ArchiveInstrumentation`を実行します。後者は既存タグを読み取り、実写真で推論しますが、タグ判断・原本を変更しません。

## 広めの自動付与（Issue #1）

タグの「自動でタグを広げる」を押すと、現在のアルバム・カメラ範囲を解析し、手動の見本に近い写真にタグを保存します。一枚ずつ承認する必要はありません。「付与済みを見る」は手動・自動の両方、「自動付与だけを見る」は推定結果を確認できます。端末内だけで処理し、写真の送信は行いません。

自動付与は精度を保証する分類ではなく、取りこぼしを減らす広めの類似度判定です。別の鳥種などへ誤って付く可能性があります。「該当しない」で除外、「判断を取り消す」でその写真の自動付与を抑制できます。訂正時は自動結果を無効化し、現在の範囲で再計算します。ほかの範囲は、その範囲で再実行してください。自動結果そのものを学習の見本には使いません。

パスは提示の保留で、自動付与を拒否する操作ではありません。停止しても保存済み結果は残り、「自動付与をすべて取り消す」で同じタグの全アルバムの自動結果だけを取り消せます。手動タグと履歴は保持します。

基準・保存・取消の契約は[自動付与の契約](docs/automatic-tag-contract.md)。`sh tests/automatic-tags.sh` と、固定テストIDの `adb shell am instrument -w -e mode automatic jp.nano.rawgallery.test/jp.nano.rawgallery.ArchiveInstrumentation` で検証します。後者は専用一時DBを使い、既存タグは変更しません。
