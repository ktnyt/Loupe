# Loupeの開発手順

理念と必須の順序は[AGENTS.md](../AGENTS.md)、工程記録は[issue-progress.md](issue-progress.md)を正とする。本書は実行時の確認方法と委譲の手順を定める。

## issueから実装へ

`gh issue list --repo ktnyt/Loupe --state all --search '対象の語句'` で重複を調べ、対応するissueがなければ既存の開発・設計テンプレートで起票する。`gh issue view 番号 --comments` で最新の要求、契約、進捗を読む。既存のissueが同じ目的を扱っていれば引き継ぐ。

issue確認時に `git status --short`、`git branch --show-current`、`git worktree list` で状態を確認し、設計・新規branch作成より先にmainを最新化する。作業中の変更を破棄したり、無関係な変更を自動でstash・コミットしたりしない。混在する場合は専用worktreeを使う。

mainを安全に操作できるworktreeで、各コマンドの成功を確認して順に実行する。

```sh
git switch main
git fetch origin main
git merge --ff-only origin/main
git rev-parse HEAD origin/main
```

最後の2つのコミットIDが一致することを確認し、issueの設計記録に基点を残す。fetch失敗、fast-forward不可、ローカルmainだけのコミットによる不一致は中断として記録し、強制リセットせず原因を確認する。

mainが別worktreeで使用中なら、そのworktreeの状態と利用状況を確認し、安全に更新できる場合だけそこで上記手順を実施する。他の作業を妨げる場合は中断して調整し、強制checkoutはしない。専用worktreeの新規作業branchは確認済みのmainのコミットから作る。既存branchで作業を再開する場合は、そのbranchと変更を保持し、更新したmainとの差分を確認して必要な取り込みを別途行う。

目的・機能・要件・不変条件・事前条件・事後条件を、issueまたは現行設計書に実装前に記す。成功条件と失敗からの復帰、UX、計測条件を含め、最もシンプルな実装方針を選ぶ。リファクタリングが必要なら、その必要性と完了条件を別issueに書き、元issueに依存先をリンクして先行実施する。単に周辺コードが気になるだけで依頼を広げない。

branchは `18/development-workflow` のように作成する。先行issueにもその番号のbranchを使う。先行リファクタリングのマージ後はmainの最新化を再実行してから本題のbranchを作成する。変更前の実機確認で再現操作・期待・実測・対象端末・アプリ版・写真枚数/形式・キャッシュ状態を残す。アプリに影響しない文書や開発ツールの変更など、省略できる場合は理由を記録する。接続できないことは「不要」の根拠にならない。

## ClaudeによるUI設計

既存の[デザイン参照](design/README.md)を読み、以下の順序で接続先を確認する。

### 接続先の確認

1. 利用者が指定したアプリ・タブ・URLがあればそこを使う。指定がなければ、今回の作業で確認済みのClaudeの対象タブ・プロジェクトを使う。アプリの起動だけが確認できている場合は、そのClaudeアプリを直接選ぶ。ブラウザが起動していることだけを根拠に、そこでClaudeを探さない。
2. 接続先が不明な場合だけ、アプリ名・タブ名・URLの一覧や関連issueの依頼先を確認する。対象の所在が分かる最小限の範囲に絞り、無関係なブラウザや画面の本文を順に読み歩かない。別経路へ切り替える前に、その経路に対象がある根拠を確認する。
3. 開いた画面がClaudeの対象プロジェクトであることと、既存依頼の進行状態を確認してから入力・送信する。Claudeアプリが開いたことだけではClaude Designへの到達とみなさない。対象不一致、利用不可、認証待ちで続行できなければ工程を中断として記録し、必要な接続先や利用者の操作を具体的に伝える。無関係な画面へ探索を広げたり、重複送信したりしない。

### 失敗後の再開

操作の失敗は該当工程に `fail`、作業の中断は `cancel` と理由を記録し、再開時は同じ作業IDで試行番号を増やす。誤った接続先を選んだ場合は、そこでの入力・送信を止め、実際に行った読取・変更・送信の範囲を確認する。

issueへの記録は履歴であり、再発防止の完了ではない。手順の不足や利用者の訂正があったときはdistillで、次の実行時に参照する規約・手順の変更が必要か判断する。必要な変更は既存の該当手順に集約し、記録だけ、または「次は注意する」だけで改善済みとしない。原因が未確定なら仮説と確認方法を残し、すべての失敗に新しい規則を追加しない。

次に同じ操作を行う際、対象へ到達した根拠、不要な画面取得や利用者の訂正の有無を既存issueで確認する。根拠付きの経路まで妨げたり探索負担が増えたりした場合は該当手順を修正・短縮し、効果がなければ変更コミットをrevertする。未実施なら効果は未確認のままにする。

### 依頼と成果物

依頼には以下を渡す。

- issueの目的、対象画面・状態・操作と契約、現在の参照HTML。
- 写真を主役にすること、文字を最小限にすること、知覚や心理を活かした自然な反応と遷移。
- 空・読み込み・成功・失敗・中断・再開、戻る操作、読み上げ、文字サイズ変更を含む必要な状態。
- HTMLとして出力する成果物と完了条件。実在の秘密情報・写真原本を渡さずダミーデータを使う。

依頼先URLまたはタスク識別子、依頼内容、開始時刻をissueへ残す。まず数分後に状態を確認し、変化がなければ間隔を延ばす（目安3〜5分、長時間なら5〜10分）。長い単一の待機で対話を止めず、他の独立作業や利用環境の待機機能を使う。応答が遅いことだけで再依頼・二重送信しない。利用不可・認証待ちは中断として記録し、別モデルの結果をClaudeの完了と見なさない。

元アーティファクトの対象画面を直接開いて依頼に添える。完成した派生HTMLは元画面と先に比較し、明示された変更要求以外の要素を現行実装の都合で削除・置換していないことを確認する。不一致があればAndroid実装前に戻す。ローカルの書き出しが描画できない場合も、元画面の確認を省かず元アプリで表示する。

完了の明示と成果物の両方を確認し、HTMLを `docs/design/` へ保存する。READMEの参照版・対象画面・確認範囲と、関連する現行設計書の契約を更新する。HTMLが開け、対象の状態と操作が収録されていることを確認する。HTMLはデザインの基準であり、Android上の動作確認の代わりにはならない。

## 実機と独立したUI・UX評価

端末を使う検証・画面操作・待機用の再生は直列に実行する。バックグラウンド実行の検証はsessionの終了と結果ログを確認してから次の端末操作へ進む。待機用動画の起動も検証中には行わない。

実装後は変更に合ったテストとビルドを行い、APK版と端末を特定してインストールする。実機で期待結果・実測結果を確認し、対象画面をキャプチャする。UI変更ではデザインHTMLの対応画面も同じ表示寸法・状態・テストデータで撮影し、左右に並べた比較画像を用意する。動きや操作は録画または操作記録を添える。機密情報を含まないテストデータで撮影する。

新しいサブエージェントを履歴なしで起動し（利用環境が対応する場合は `fork_turns: none`）、次の指示と成果物だけを渡す。実装者の見立て、弁明、予想する合否は渡さない。

> 添付は基準デザインと実機キャプチャの比較です。対象の操作目的は〈利用者の目的〉です。配置・寸法・余白・色・形・文字・画像・各状態を比較し、完全一致を目標として不一致を位置と根拠付きで列挙してください。操作記録も使い、迷い、押しやすさ、反応、待ち時間、中断・復帰、読み上げを含むUXを評価してください。確認できない項目は未検査としてください。ファイルは変更せず、合否と修正項目を返してください。

見えていない操作性を静止画だけで合格にしない。写真内容・OS領域・描画方式など比較条件の差も具体的に報告し、差を一括無視しない。要件に関係する不一致は修正し、再インストール・再撮影・再評価する。明らかにissueの本質から外れた指摘だけ、その根拠をissueへ記録して追跡を分ける。「だいたい似ている」を完全一致と報告しない。

## Cold ReviewとSecurity Review

cold-reviewの手順を用い、開発履歴を継承しないレビュアーへ対象worktree、比較元コミット、issueの要求と契約、読取専用の範囲を渡す。差分に加え、文書と実装の一致、不要な仕組みも確認する。

その後security-reviewを使い、変更した範囲の入力・権限・保存/共有・外部送信・ログ・秘密情報・依存関係を確認する。対象外の観点は理由を残す。変更していないアプリ全体まで検査済みとしない。

それぞれ指摘の発生条件と影響を確かめ、対象issueに必要な修正を行い、同じ範囲を再レビューする。レビュー結果・採否・根拠・未検査・再試行番号をissueへ残す。範囲外でも重要なら別issueに起票してリンクする。未解決の範囲内指摘、実施不能の必須検証があればマージせず中断を記録する。Security Review後のコード修正も必要なテストとCold Reviewへ戻す。

## 計測と完了

アプリの計測は[診断ログ](diagnostics.md)を使い、各issueで操作開始から利用者に結果が届くまでの時間、成功/失敗、待ち・中断・再試行、対象機能の負荷や件数を定義する。必要なイベントがなければ先に計測を整える。測定値には単位、端末、アプリ版、入力条件、サンプル数を付ける。アプリのあらゆる事象を計測対象として検討し、未計測の範囲もissueに明記する。写真原本・位置情報・個人情報を計測のために収集しない。

開発は進捗CLIで設計、変更前確認、Claudeの待ち時間を含む設計、実装、インストール、実機確認、各レビュー、追加修正、PR/マージの経過時間と試行回数を残す。取得できるビルド時間・テスト時間・利用量も単位とともにissueへ記録し、取得できなければ未計測とする。経過時間は稼働時間とは異なり、並行工程を加算しない。次回見積もりでは似た条件の実測とばらつきを使う。

進捗reportを実施内容と照合し、PRテンプレートへ根拠のリンクを記入する。完了条件を全て満たすissueだけ `Closes #番号` を記す。PRの差分・チェック・レビュー状態を確認し、必要なチェックが通ってから通常のマージを行う。保護ルールや失敗チェックを迂回しない。マージ後にPRの状態とissueの自動クローズを再取得して確認する。

この仕組みは規約・既存CLI・テンプレートによる運用であり、全操作を自動実行・強制するものではない。次のUI開発でClaude依頼から実機比較まで通し、記録漏れ・手戻り・工程時間・記録負担をissueで評価する。負担が効果に見合わなければ重複手順を減らす。戻すときは本変更のコミットをrevertし、過去のissue記録は保持する。
