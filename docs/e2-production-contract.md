# IDrive e2 原本バックアップの本番運用契約

[#117](https://github.com/ktnyt/Loupe/issues/117) の初回運用はJPEG・RAW・動画のバックアップと復元、小さいサムネイルを端末に残すJPEGの原本整理を含む。IDrive e2東京への単一端末からの書き込みと、端末SQLiteでの閲覧を前提とする。端末で扱う既存の拡張子を対象とし、復元一覧へ保管を照合した原本をすべて載せる。復元一覧の新形式は512 MiBを超える原本を扱う。照合する間は一時領域に原本のサイズの空き容量が必要で、原本の一時ファイルへの書き込みで端末の空き容量が64 MiBを下回る場合は中止する。容量が足りない場合は原本を残して失敗として表示する。D1、複数端末の同時更新、順位・タグ・編集情報の機種変更は後続。

## 原本を保管し、中断後に再開する

対象と保存先は利用者が確認して開始する。写真IDと保管先・原本の内容を紐付け、撮影日や同名だけで写真を統合しない。端末URIは端末外の識別子に使わない。原本は転送前に処理待ちを永続化し、同じ転送の再試行は同じ参照を照合する。PUTには原本のSHA-256を付ける。保存したバージョンを指定するHEADで版・サイズ・SHA-256を照合し、確認結果を端末記録に保存して確定する。HEADにSHA-256またはサイズがなければ、同じ版を全量GETして照合する。不一致があれば保存済みにしない。未確認、新規保管済み、カタログ公開済みを区別する。

中断・応答喪失後は照合して続行する。単一PUTの途中で中断し、保存版が作られていない場合は再試行時に先頭から送信する。バイト位置を保持して再開する処理は別途設計する。認証拒否、内容不一致、存在が確定しない応答では再送で解決しない。通信停止時に転送が待ち続けないことを試験する。端末のキーにはデータの恒久削除・バケット設定変更を許さず、読み戻しを試験用バケットで検証する。

## 旧端末なしで一覧と原本を取り戻す

自動バックアップを有効にすると、AndroidのJobSchedulerがMediaStoreの変更を監視する。写真や動画の追加・変更時は、従量制でない回線などの実行条件を満たした時点で同期する。監視は端末の起動とアプリの更新後にも登録する。Loupeを開いた時点で監視が欠けていれば再登録し、その間の変更を確認するジョブを予約する。変更がない間はLoupeの監視プロセスを常駐させず、取りこぼしに備えた確認は12時間周期で予約する。容量整理を有効にした場合は、日数経過でも整理候補が変わるため15分周期とする。処理が残る場合と失敗時は次の実行を予約する。容量整理が無効で、同期・復元一覧の公開・必要なプレビューの保存が完了し、写真の変更監視を維持できた場合は、不要になった失敗時の再試行予約を取り消す。容量整理が無効で、同期対象に差分やプレビューの再作成、復元一覧への未公開分がなければe2に接続せず終了する。

自動バックアップで未公開の保管記録がある場合と手動保存の直後に、照合済みの原本を含む復元一覧を公開する。公開に失敗しても、新しい原本の転送を続ける。失敗と未公開の状態を表示し、次の同期や手動の「復元一覧をクラウドに保存」で一覧の公開を再試行する。未公開の保管記録も容量整理の候補もない定期同期では、復元一覧の分割ファイルを読み込まない。容量整理の候補がある場合は、有効な最新版を照合してから原本を整理する。

長い自動バックアップは実行中の転送を完了させ、未処理の原本を次のAndroidジョブへ引き継ぐ。同じ保存先でMediaStoreの対象と変更履歴が一致する場合は、確認できた位置と件数から続ける。対象や保存先が変わった場合は、永続化済みの保管記録を使って一覧の先頭から確認する。引き継ぐジョブにも従量制でない回線と空き容量の条件を適用する。

新しい環境では同じバケットへ接続し、「クラウドから復元一覧を取得」から復元点の日時と件数を確認する。各原本の「復元」から別ファイルに保存する。保存先の選択中に画面が再作成されても、カタログのサイズとSHA-256を使い、書き出し前と書き出し後の原本を照合する。

旧形式の復元一覧を読み取り、次の公開で新形式へ引き継ぐ。新形式では最大256件・256 KiBの分割ファイルを使い、版IDとSHA-256を記録した索引を最後に条件付きで公開する。分割数は最大512で、件数の上限は131,072件。ファイル名などで分割のバイト数が先に埋まる場合は、これより少ない件数で実際の上限に達する。分割数・索引サイズの上限を超えた世代は公開に失敗する。旧版では50,000件を超える現行形式の一覧を読めないため、大規模な一覧を使う前に復元用のLoupeも更新する。バージョニングで前世代を保持し、復元時に最新が検証できない場合は直前の有効な世代を探す。公開と端末の容量整理には有効な最新版が必要。取得にはバケットのバージョニング、索引・分割ファイル・原本の版、前世代の一覧を読む権限が必要。

写真ID、保存先、キー、版、サイズ、SHA-256、撮影情報、プレビュー参照を、検証可能なカタログとして保存する。版・ライブラリ・件数・内容を読み戻した世代だけを復元点とし、不完全な最新世代は前の有効な世代に戻す。復元時は一時領域で全体を検証してからSQLiteに反映し、既存データとの衝突は保留する。プレビューは先に表示し、原本は必要になった時点で版を指定して取得・照合する。

新端末での初回復元では、e2から最後の有効なカタログと原本の保存版を読み出し、端末に保存する。loupe-testでの同期・復元試験では、設定済みの読み書きキーを共用する。キーの失効・再発行は、端末紛失や漏えいへの対応手順を検証する段階で行う。復元点の時刻を提示する。許容する未保管時間、カタログ反映時間、復元時間は普段に近い運用条件で測って決める。

## 端末原本の整理と既存写真の移行

端末原本の自動整理は利用者がバックアップとは別に有効化する。対象の保存版を再取得して照合し、検証済みカタログに同じ原本の版と照合値が収録され、小さいサムネイルを端末から読み戻せる状態で保持した写真だけを整理候補とする。サムネイルはキャッシュの消去やアプリの再起動を経ても、オフラインで一覧を表示できる領域に置く。閲覧索引や復元直後の記録は整理許可に流用しない。

通常版の自動整理は初期状態で無効。初回は主ストレージのMediaStoreに登録されたJPEGを対象とし、JPEGの長辺256px以下のサムネイルを残す。利用者が確認したバケットと保存期間を同意に紐づける。保存期間の変更や自動バックアップの一時停止で容量整理も停止する。復元済みのJPEGには書き出し時点から保存期間を適用する。

整理対象の原本と権限を削除直前に確かめる。照合後の差し替えを検出した原本や、権限・照合・永続化のいずれかを確認できない原本は保持する。削除の実行前に途中状態を永続化し、再開時には対象の有無と同一性に応じて記録を確定する。試験用JPEGで、対象原本だけが消えること、条件未達の原本が残ること、削除後のオフライン表示、旧端末データを持たない環境での原本復元とSHA-256照合を確認する。途中停止は実機で代表例を確認し、権限不足・DB失敗・差し替えの個別分岐は自動テストで確認する。

既存写真はAmazonとHDDを保持したまま少量から移行し、端末からの新規バックアップと別の台帳で扱う。既存e2オブジェクトはキー名を変えて再送せず、実際の保存版とカタログを照合して再利用する。台帳の全件照合と別端末での復元を経て、Amazonへの依存解消を判定する。

## Amazon Photosから保管済みの原本を復元一覧へ載せる

`loupe/migration/amazon-photos/v1/` の写真用台帳と `loupe/migration/amazon-photos/videos/v1/` の動画用台帳は、Windows側で原本の版指定取得とSHA-256照合が完了した項目を示す。`scripts/e2-migration-catalog.py` は同じバケットにある両方の台帳を読み、Loupeが対応する形式の原本は保存版とサイズを照合して通常版の復元索引へ変換する。撮影日が未設定の記録は0を保つ。復元索引の読み取りで取得した行は、端末の容量整理に必要な保管記録を作らない。

東京のIDrive e2の環境変数を読み込んだPython環境（Boto3 1.40以上）で、先に読み取りを行う。

```sh
python3 scripts/e2-migration-catalog.py --bucket loupe-test
```

明示的な公開では `--publish` を追加する。両台帳の合計件数（保留した動画を含む）の一致を求めるときは `--expect-count` を指定する。両台帳の対象を先に列挙し、原本の照合中に追加された個別記録は次の実行で取り込む。個別記録は作成後に同じキーで差し替えない運用を前提とし、索引公開直前の再列挙で差し替えを検出した場合は中止する。元の原本と個別記録、既存のv1索引は書き換えない。現在のv1/v2の行を保持し、競合や検証失敗では索引の更新を中止する。分割ファイルの版指定読み戻しに成功したあとで索引を条件付きで更新する。公開途中で止まっても再実行時は同じ内容の分割ファイルを再利用する。原本のSHA-256は移行時の照合記録を使い、通常版からの復元時に原本を再照合する。

## 試験バケットの事前確認

バージョニングを有効にし、原本と復元用カタログに失効ルールが適用されないことを確認する。東京の試験バケットを指定し、設定を読み取れるAWS CLIプロファイルで事前確認を実行する。

```sh
python3 scripts/e2-bucket-preflight.py --profile TEST_PROFILE --bucket TEST_BUCKET
```

検査はバージョニングとライフサイクル設定を取得する。有効な失効ルールがあれば、対象プレフィックスと条件を個別に確認する。バケットの公開設定、端末用キーの権限、保存版の読み戻しはそれぞれ別に検証する。
