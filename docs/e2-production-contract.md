# IDrive e2 オリジナルバックアップの本番運用契約

[#117](https://github.com/ktnyt/Loupe/issues/117) の初回運用はJPEG・RAW・動画のバックアップと復元、小さいサムネイルを端末に残すJPEGのオリジナル整理を含む。IDrive e2東京への単一端末からの書き込みと、端末SQLiteでの閲覧を前提とする。端末で扱う既存の拡張子を対象とし、復元一覧へ保管を照合したオリジナルをすべて載せる。復元一覧の新形式は512 MiBを超えるオリジナルを扱う。照合する間は一時領域にオリジナルのサイズの空き容量が必要で、オリジナルの一時ファイルへの書き込みで端末の空き容量が64 MiBを下回る場合は中止する。容量が足りない場合はオリジナルを残して失敗として表示する。D1、複数端末の同時更新、順位・タグ・編集情報の機種変更は後続。

## オリジナルを保管し、中断後に再開する

対象と保存先は利用者が確認して開始する。写真IDと保管先・オリジナルの内容を紐付け、撮影日や同名だけで写真を統合しない。端末URIは端末外の識別子に使わない。オリジナルは転送前に処理待ちを永続化し、同じ転送の再試行は同じ参照を照合する。PUTにはオリジナルのSHA-256を付ける。保存したバージョンを指定するHEADで版・サイズ・SHA-256を照合し、確認結果を端末記録に保存して確定する。HEADにSHA-256またはサイズがなければ、同じ版を全量GETして照合する。不一致があれば保存済みにしない。未確認、新規保管済み、カタログ公開済みを区別する。

中断・応答喪失後は照合して続行する。単一PUTの途中で中断し、保存版が作られていない場合は再試行時に先頭から送信する。バイト位置を保持して再開する処理は別途設計する。認証拒否、内容不一致、存在が確定しない応答では再送で解決しない。通信停止時に転送が待ち続けないことを試験する。端末のキーにはデータの恒久削除・バケット設定変更を許さず、読み戻しを試験用バケットで検証する。

## 旧端末なしで一覧とオリジナルを取り戻す

自動バックアップを有効にすると、AndroidのJobSchedulerがMediaStoreの変更を監視する。写真や動画の追加・変更時は、従量制でない回線などの実行条件を満たした時点で同期する。監視は端末の起動とアプリの更新後にも登録する。Loupeを開いた時点で監視が欠けていれば再登録し、その間の変更を確認するジョブを予約する。変更がない間はLoupeの監視プロセスを常駐させず、取りこぼしに備えた確認は12時間周期で予約する。容量整理を有効にした場合は、日数経過でも整理候補が変わるため15分周期とする。処理が残る場合と失敗時は次の実行を予約する。容量整理が無効で、同期・復元一覧の公開・必要なプレビューの保存が完了し、写真の変更監視を維持できた場合は、不要になった失敗時の再試行予約を取り消す。容量整理が無効で、同期対象に差分やプレビューの再作成、復元一覧への未公開分がなければe2に接続せず終了する。

自動バックアップで未公開の保管記録がある場合と手動保存の直後に、照合済みのオリジナルを含む復元一覧を公開する。公開に失敗しても、新しいオリジナルの転送を続ける。失敗と未公開の状態を表示し、次の同期や手動の「復元一覧をクラウドに保存」で一覧の公開を再試行する。未公開の保管記録も容量整理の候補もない定期同期では、復元一覧の分割ファイルを読み込まない。容量整理の候補がある場合は、有効な最新版を照合してからオリジナルを整理する。

長い自動バックアップは実行中の転送を完了させ、未処理のオリジナルを次のAndroidジョブへ引き継ぐ。同じ保存先でMediaStoreの対象と変更履歴が一致する場合は、確認できた位置と件数から続ける。対象や保存先が変わった場合は、永続化済みの保管記録を使って一覧の先頭から確認する。引き継ぐジョブにも従量制でない回線と空き容量の条件を適用する。

新しい環境では同じバケットへ接続し、「クラウドから復元一覧を取得」から復元点の日時と件数を確認する。各オリジナルの「復元」から別ファイルに保存する。保存先の選択中に画面が再作成されても、カタログのサイズとSHA-256を使い、書き出し前と書き出し後のオリジナルを照合する。

旧形式の復元一覧を読み取り、次の公開で新形式へ引き継ぐ。新形式では最大256件・256 KiBの分割ファイルを使い、版IDとSHA-256を記録した索引を最後に条件付きで公開する。分割数は最大512で、件数の上限は131,072件。ファイル名などで分割のバイト数が先に埋まる場合は、これより少ない件数で実際の上限に達する。分割数・索引サイズの上限を超えた世代は公開に失敗する。旧版では50,000件を超える現行形式の一覧を読めないため、大規模な一覧を使う前に復元用のLoupeも更新する。バージョニングで前世代を保持し、復元時に最新が検証できない場合は直前の有効な世代を探す。公開と端末の容量整理には有効な最新版が必要。取得にはバケットのバージョニング、索引・分割ファイル・オリジナルの版、前世代の一覧を読む権限が必要。

写真ID、保存先、キー、版、サイズ、SHA-256、撮影情報、プレビュー参照を、検証可能なカタログとして保存する。版・ライブラリ・件数・内容を読み戻した世代だけを復元点とし、不完全な最新世代は前の有効な世代に戻す。復元時は一時領域で全体を検証してからSQLiteに反映し、既存データとの衝突は保留する。プレビューは先に表示し、オリジナルは必要になった時点で版を指定して取得・照合する。

新端末での初回復元では、e2から最後の有効なカタログとオリジナルの保存版を読み出し、端末に保存する。loupe-testでの同期・復元試験では、設定済みの読み書きキーを共用する。キーの失効・再発行は、端末紛失や漏えいへの対応手順を検証する段階で行う。復元点の時刻を提示する。許容する未保管時間、カタログ反映時間、復元時間は普段に近い運用条件で測って決める。

## 端末オリジナルの整理と既存写真の移行

端末オリジナルの自動整理は利用者がバックアップとは別に有効化する。対象の保存版を再取得して照合し、検証済みカタログに同じオリジナルの版と照合値が収録され、小さいサムネイルを端末から読み戻せる状態で保持した写真だけを整理候補とする。サムネイルはキャッシュの消去やアプリの再起動を経ても、オフラインで一覧を表示できる領域に置く。閲覧索引や復元直後の記録は整理許可に流用しない。

通常版の自動整理は初期状態で無効。初回は主ストレージのMediaStoreに登録されたJPEGを対象とし、JPEGの長辺256px以下のサムネイルを残す。利用者が確認したバケットと保存期間を同意に紐づける。保存期間の変更や自動バックアップの一時停止で容量整理も停止する。「端末に写真を残す期間」から7日・30日・90日を選べる。未設定時は7日とし、既存の期間は選び直すまで保持する。期間の変更後に整理を再開するには、現在の期間で利用者が改めて有効にする。復元済みのJPEGには書き出し時点から保存期間を適用する。

旧Amazon Photosの容量整理が有効だった端末では、以前のe2同意だけで整理を始めない。確認画面で利用者が改めて有効にした場合に限り、バケットと保存期間に対する同意を記録する。設定の書き込み前にアプリ専用領域へ整理を止めるファイルを作り、ファイルと親ディレクトリを同期する。設定の保存が成功し、そのファイルの削除と親ディレクトリの同期、削除後の不在を確認してから有効にする。設定の保存が失敗した場合はファイルを残す。ファイルがある場合や状態を読み取れない場合は整理しない。アプリ起動や自動バックアップをきっかけに有効化を完了させることはない。旧Amazon Photosの容量整理が無効だった端末では、既存のe2同意を引き続き使う。

旧Amazon Photosの容量整理が有効だった端末で新しい同意を取り消すときも、先に停止用のファイルを同期する。ファイルを同期できなければ設定を変更せず、その起動中の容量整理を止めて、設定結果を確認できないと表示する。有効化の最後にファイルの削除や同期の結果を確認できなかった場合も、その起動中は整理しない。次の起動時は保存された同意とファイルの状態から判定するため、利用者が結果表示を見る前にアプリが終了しても、有効化が済んでいる場合がある。

整理対象のオリジナルと権限を削除直前に確かめる。照合後の差し替えを検出したオリジナルや、権限・照合・永続化のいずれかを確認できないオリジナルは保持する。削除の実行前に途中状態を永続化し、再開時には対象の有無と同一性に応じて記録を確定する。試験用JPEGで、対象オリジナルだけが消えること、条件未達のオリジナルが残ること、削除後のオフライン表示、旧端末データを持たない環境でのオリジナル復元とSHA-256照合を確認する。途中停止は実機で代表例を確認し、権限不足・DB失敗・差し替えの個別分岐は自動テストで確認する。

既存写真はAmazonとHDDを保持したまま少量から移行し、端末からの新規バックアップと別の台帳で扱う。既存e2オブジェクトはキー名を変えて再送せず、実際の保存版とカタログを照合して再利用する。台帳の全件照合と別端末での復元を経て、Amazonへの依存解消を判定する。

## Amazon Photosから保管済みのオリジナルを復元一覧へ載せる

LoupeからAmazon Photosへのログイン・同期・原本取得は終了した。以前の保管記録とプレビューは端末に保持する。Amazon Photosに保管したオリジナルはAmazon Photosで確認し、IDrive e2に移行済みのオリジナルはLoupeの「IDrive e2」の復元一覧から書き出せる。

`loupe/migration/amazon-photos/v1/` の写真用台帳と `loupe/migration/amazon-photos/videos/v1/` の動画用台帳は、Windows側でオリジナルの版指定取得とSHA-256照合が完了した項目を示す。`scripts/e2-migration-catalog.py` は同じバケットにある両方の台帳を読み、Loupeが対応する形式のオリジナルは保存版とサイズを照合して通常版の復元索引へ変換する。撮影日が未設定の記録は0を保つ。復元索引の読み取りで取得した行は、端末の容量整理に必要な保管記録を作らない。

東京のIDrive e2の環境変数を読み込んだPython環境（Boto3 1.40以上）で、先に読み取りを行う。

```sh
python3 scripts/e2-migration-catalog.py --bucket loupe-test
```

明示的な公開では `--publish` を追加する。両台帳の合計件数（保留した動画を含む）の一致を求めるときは `--expect-count` を指定する。両台帳の対象を先に列挙し、オリジナルの照合中に追加された個別記録は次の実行で取り込む。個別記録は作成後に同じキーで差し替えない運用を前提とし、索引公開直前の再列挙で差し替えを検出した場合は中止する。元のオリジナルと個別記録、既存のv1索引は書き換えない。現在のv1/v2の行を保持し、競合や検証失敗では索引の更新を中止する。分割ファイルの版指定読み戻しに成功したあとで索引を条件付きで更新する。公開途中で止まっても再実行時は同じ内容の分割ファイルを再利用する。オリジナルのSHA-256は移行時の照合記録を使い、通常版からの復元時にオリジナルを再照合する。

### 追加分を自動で公開する

既存のe2設定を読み込める常時稼働ホストで、監視モードをバックグラウンドサービスから起動する。試験先の例は次のとおり。

```sh
python3 scripts/e2-migration-catalog.py --bucket loupe-test --publish --watch
```

既定では1回の確認を終えてから15分後に再確認する。`--watch 60` のように秒数を指定できる。台帳と現行索引を確認し、追加すべき行がある場合だけ公開する。初回に照合した台帳は、同じプロセス内でキー・ETag・サイズが一致していれば再利用する。現行の一覧から消えた行を復旧する場合は、保存版を再確認する。通信エラーや他の端末の公開との競合があれば次の確認で再試行する。アプリからすでに取り込んでいる一覧は、更新時に最新世代を取得する。

監視はバケットごとに明示して起動する。ホストが停止・スリープ中は公開も止まり、起動時の確認でその間の追加を取り込む。本番運用には `loupe-data` の分割ファイルと索引への書き込みが必要。オリジナル・移行台帳は読み取りで照合する。

## 試験バケットの事前確認

バージョニングを有効にし、オリジナルと復元用カタログに失効ルールが適用されないことを確認する。東京の試験バケットを指定し、設定を読み取れるAWS CLIプロファイルで事前確認を実行する。

```sh
python3 scripts/e2-bucket-preflight.py --profile TEST_PROFILE --bucket TEST_BUCKET
```

検査はバージョニングとライフサイクル設定を取得する。有効な失効ルールがあれば、対象プレフィックスと条件を個別に確認する。バケットの公開設定、端末用キーの権限、保存版の読み戻しはそれぞれ別に検証する。
