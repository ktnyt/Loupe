# IDrive e2 原本バックアップの本番運用契約

対象: [#117](https://github.com/ktnyt/Loupe/issues/117)。初回の範囲は端末原本を保持した写真バックアップと復元。IDrive e2東京への単一端末からの書き込みと、端末SQLiteでの閲覧を前提とする。動画、D1、複数端末の同時更新は初回の対象外。RAWは現行対応機種、JPEGは読み取れる原本を対象とし、既存転送の512 MiB上限を維持する。順位・タグ・編集設定の機種変更対応は別途契約を定める。対象外を同期済みとして表示しない。

## 原本を保管し、中断後に再開する

対象と保存先は利用者が確認して開始する。写真IDと保管先・原本の内容を紐付け、撮影日や同名だけで写真を統合しない。端末URIは端末外の識別子に使わない。原本は転送前に処理待ちを永続化し、同じ転送の再試行は同じ参照を照合する。確定の条件は保存版の取得、サイズ・SHA-256の一致、端末記録の保存成功。未確認、新規保管済み、カタログ公開済みを区別する。

中断・応答喪失後は照合して続行する。認証拒否、内容不一致、存在が確定しない応答では再送で解決しない。通信停止時に転送が待ち続けないことを試験する。端末のキーにはデータの恒久削除・バケット設定変更を許さず、読み戻しとキー再発行を試験用バケットで検証する。

## 旧端末なしで一覧と原本を取り戻す

保管元で「復元一覧をクラウドに保存」を選び、保存先を確認する。保管済みの写真を増やしたときは再度保存する。新しい環境では同じバケットへ接続し、「クラウドから復元一覧を取得」を選ぶ。表示された復元点の日時と件数を確認し、写真ごとの「復元」から別ファイルに保存する。

現在のカタログは1バケットにつき1ファイルで、512 KiB・2,000件を上限とする。バージョニングで前世代を保持し、最新を取得できない場合は世代一覧の先頭16項目から検証できる版を探す。取得には保存先のバージョニング、カタログと原本の版、前世代の一覧を読む権限が必要。永続プレビュー、キー再発行の実測、大規模カタログの設計は後続工程で扱う。

写真ID、保存先、キー、版、サイズ、SHA-256、撮影情報、プレビュー参照を、検証可能なカタログとして保存する。版・ライブラリ・件数・内容を読み戻した世代だけを復元点とし、不完全な最新世代は前の有効な世代に戻す。復元時は一時領域で全体を検証してからSQLiteに反映し、既存データとの衝突は保留する。プレビューは先に表示し、原本は必要になった時点で版を指定して取得・照合する。

新端末の初回復元は読み取り専用。旧端末の書き込みキーを失効でき、最後の有効世代と原本へアクセスできることを実測する。最新の復元点の時刻を提示する。許容する未保管時間、カタログ反映時間、復元時間、電池・回線負荷の数値基準は、実データの測定条件とあわせて運用開始前に確定する。

## 端末原本の整理と既存写真の移行

端末原本の自動整理は独立した有効化とする。対象の保存版を再取得して照合し、永続プレビューと検証済みカタログを確認でき、端末原本が照合時から変わっていない場合にだけ整理候補とする。整理の直前・直後の中断、権限取消、DB失敗、原本の差し替え、整理後の編集・共有を専用の試験データで検証する。閲覧索引や復元直後のレコードは整理許可に流用しない。

既存写真はAmazonとHDDを保持したまま少量から移行し、端末からの新規バックアップと別の台帳で扱う。既存e2オブジェクトはキー名を変えて再送せず、実際の保存版とカタログを照合して再利用する。台帳の全件照合と別端末での復元を経て、Amazonへの依存解消を判定する。

## 試験バケットの事前確認

バージョニングを有効にし、原本と復元用カタログに失効ルールが適用されないことを確認する。東京の試験バケットを指定し、設定を読み取れるAWS CLIプロファイルで事前確認を実行する。

```sh
python3 scripts/e2-bucket-preflight.py --profile TEST_PROFILE --bucket TEST_BUCKET
```

検査はバージョニングとライフサイクル設定を取得する。有効な失効ルールがあれば、対象プレフィックスと条件を個別に確認する。バケットの公開設定、端末用キーの権限、保存版の読み戻しはそれぞれ別に検証する。
