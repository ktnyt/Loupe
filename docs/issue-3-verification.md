# 連写表示の検証範囲

0.17.9 (34)、Android 16 / 25128PNA1Gで、0.17.8から引き継いだ画像読込の修正を検証した。工程履歴は[issue #3](https://github.com/ktnyt/Loupe/issues/3)、作業IDは `20261025-issue3-preview`。元の症状と処理内訳は[原因調査](issue-3-investigation.md)を参照。

## 契約と結果

離れた一覧の未着手要求を生成前に破棄し、連写の先頭写真を残りのサムネイルより先に表示する。画像の失敗は再試行可能にし、別画面へ移った後の結果を混入させない。写真原本・順位・タグ・選択を変更しない。

| 条件 | burst.open→最初の実画像frame commit | 補足 |
| --- | ---: | --- |
| RAW6、先頭compact hit・残り5枚miss、組A | 53.204ms | 前景キュー0.108ms、repository lock0.023ms |
| 同条件、別のRAW6組B | 36.878ms | 録画で先頭実写真と残りサムネイル読込中の状態を確認 |
| 通常の一覧タップ、JPEG6 | 37.000ms | touch UP→open 0.375ms、合計37.375ms |
| スクロール先の別組、JPEG9 | 34.782ms | touch UP→open 0.942ms、合計35.724ms |

各組1回。RAWは計測用呼出しでありタップ時間を含まない。JPEGの先頭はメモリmiss、ディスクキャッシュ状態は厳密に揃えていない。RAW2組は残り5枚が未生成の条件をコードで確認した。キャッシュ・原本の削除は行っていない。元の2.666秒のRAW6とは別の原本なので、厳密な同一原本での改善比には使わない。元のJPEG16と同一組の再測定でもない。

[匿名ログ抜粋](diagnostics/issue-3-verification-trace.jsonl)は各open前5ms〜後150ms。写真ID・URI・ファイル名を含めない。回収時の破損行・droppedは0。録画と写真はローカルに留め、リポジトリへ保存しない。測定時の端末温度は31.3℃、待機動画は終了状態。

frame commitはGPUへの提出で、物理ディスプレイの表示完了時刻ではない。仮画像の `image.placeholder` と実画像の `image.frame_commit` を分けている。取得した時間は実画像のものである。

## 回帰確認

実機の `mode burst` で以下が成功した。

- 36件の旧一覧要求を、存在しない原本への読込を行う前に取消。
- 保存済みThumbHashを原本なしで復元し、版が変わった画像や無効な対象へ適用しない。
- 背景生成を待機させたまま、別repositoryの前景キャッシュmissを完了。
- 同時公開・工程途中の取消・合成原本のバイト不変。
- hero描画前にstrip読込を開始しない。選択変更を優先し、失敗の再試行を表示し、離れた画面の処理を継続しない。

これらは合成データで失敗・競合を作る試験で、実写真を破損させる検証ではない。

## 未確認

全写真・全形式・他機種での上限時間、完全cold条件、元のJPEG16と同一組での再現、長期の背景生成完走・電池/発熱影響は未確認。ThumbHashの視覚効果全体や状態表示の再設計は本検証の対象外（#17）。小さな画像の表示が速いことだけを、全条件の解決とは扱わない。

## 派生画像の破損からの復帰

0.17.10 (35)では、prepared画像のデコードが失敗すると、その派生WebPとメタデータを無効化する。再試行時には原本から再生成する。元のPreviewと現在のファイルのdevice/inodeが違う場合は、並行して公開された置換ファイルを削除しない。通常の原本・archive由来Previewには無効化処理を付けない。

実機で合成派生WebPだけを破損させ、失敗後の次回読込成功、正常原本バイト不変、原本扱いPreviewのデコード失敗時にもファイルを保持することを確認した。仮画像試験は読込開始後にUIキューを止めて無効化し、反映時の2回目の条件検査と適用0件を確認した。以前のactive=falseから始める試験だけでは、この反映直前の条件は検証できていなかった。

同版の通常JPEG6再確認はopen→実画像frame commit 40.226ms（キャッシュ生成済みの回帰確認、改善比には使用しない）。ビルド・lint・burst実機回帰が成功。
