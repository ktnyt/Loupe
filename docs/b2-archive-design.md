# B2と端末SQLiteによる写真の保管・復元

2026年11月4日（日本時間）。設計の基点は `c2ff9f8`。[設計issue #75](https://github.com/ktnyt/Loupe/issues/75)。実装前の設計案。

## 文脈と範囲

Amazon Photosへの非公式接続が将来使えなくなっても、原本を保存し、端末容量を整理した写真を閲覧・編集・共有できるようにする。移行元は約856GB、数万枚。容量と枚数は移行時に再取得する。既存のLoupeでは、`ArchiveStore` が原本の照合結果と復元先を保持し、`GalleryIndex` が端末写真と保管記録から一覧を構築する。端末移行ではアプリのDBとファイルが除外される。[現行設計 P1・P5・P6](current-design.md)、[端末移行設定](../app/src/main/res/xml/data_extraction_rules.xml)。

合意済みの構成はB2と端末SQLite。D1同期は後続。以下のB2直接接続、単一端末からの書き込み、カタログの保存形式、移行順は今回の提案とする。保存先の実設定、既存原本の取得可能範囲、転送性能は実装前の試行で確認する。

| 担当 | 保持するデータ・役割 |
| --- | --- |
| B2の非公開バケット | 原本、小さな閲覧用プレビュー、機種変更用のカタログ |
| 端末の `ArchiveStore` | 永続ID、端末写真との対応、原本の保存先・照合結果、再開状態 |
| 端末の `GalleryIndex` | 撮影日・フォルダ・機種などで閲覧するための再構築可能な索引 |
| 端末のキャッシュ | 表示範囲のプレビューと取得済み原本。保持容量の管理は既存の責務に合わせる |

## B1 原本を保管して取り出せる

- 機能・要件。選んだRAW/JPEGをB2に保存し、必要時に同じバイト列を取得する。保存結果が不明でも、再開時に別の写真として二重登録しない。現行の原本照合契約を継承する。
- 不変条件。写真の永続IDと保存先を分ける。端末URIは端末内でのみ使う。元のファイル名が同じでも別の写真を上書きしない。ハッシュの一致は内容の照合に使い、異なるアルバム内の写真を統合する判断には使わない。
- 事前条件。利用者が対象フォルダと保存先を指定し、読み取りを許可する。原本は送信前にサイズとSHA-256を確定する。初回の対象形式とサイズ上限は現行の契約に合わせる。
- 事後条件。原本のキーと照合値を `pending` として先に永続化する。B2から取得した原本の版、サイズ、SHA-256を確認し、プレビューも保存・確認できた後、`verified` を記録する。以降の原本取得は照合した版を指定する。原本は一時ファイルで検証し、成功したものだけ編集・共有に渡す。
- 再試行。キーは写真IDと内容のSHA-256から決める。応答を失った場合は同じキーを照会し、見つかった原本の内容を検証してから続きへ進む。不一致や認証エラーは保留とし、不一致のオブジェクトを上書きしない。存在しないと確認できた場合のみ再送する。同じ写真の処理は直列化する。B2は同名の再送でも版を作るため、論理的な重複防止と保存版の増加を区別する。
- 失敗時。認証失敗は転送を停止して再設定を求める。一時的な通信失敗は間隔を空けて再開する。転送途中のデータや復元不能な原本は完了扱いにしない。取得済みの一覧とプレビューを引き続き利用できる。

B2への接続はS3互換APIを使う案とする。専用バケットに絞った標準キーを端末で設定し、Android Keystoreの鍵で保護したアプリ内領域へ保存する。アプリには原本の完全削除やバケット設定を変更する権限を付けない。書き込み権限でオブジェクトを隠せる操作があるため、原本は照合した版を参照し、バケットの保持設定でその版が消えないことを確認する。読み取り・書き込み・必要な列挙に絞れることを試験バケットで確認する。エンドポイントは対象リージョンのB2公式HTTPSホストに限定し、外部URLへの認証情報付き転送を拒否する。ログ・バックアップには秘密情報や写真の内容を入れない。キー再発行後に元のバケットへ戻れることを確認する。[S3互換API](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api)、[キーの制限](https://www.backblaze.com/docs/cloud-storage-application-keys)、[ファイルの版](https://www.backblaze.com/docs/cloud-storage-file-versions)、[キーの操作権限](https://www.backblaze.com/docs/cloud-storage-application-key-capabilities)、[版を指定した取得](https://www.backblaze.com/apidocs/s3-get-object)。

## B2 写真を待たずに探し、必要な原本を開ける

- 機能・要件。同期や通信待ちでも、前回の一覧を開き、端末の写真と保管済み写真を探せる。初回のサムネイル取得は表示中の範囲を優先する。
- 不変条件。一覧の表示とフィルタは端末SQLiteから行う。通常の起動・スクロール・検索ではB2の全件列挙を呼ばない。閲覧索引と、端末原本の整理を許可する保管記録は分ける。
- 事前条件。端末写真または復元済みの保管記録がある。ネットワークが必要な写真には、既存プレビューか取得可能なプレビュー参照がある。
- 事後条件。バックグラウンドで索引を更新し、完成した一覧を反映する。取得途中・オフライン・認証切れでも既存の一覧を消さない。原本が必要な操作では取得状態を区別し、失敗時はプレビューを残す。
- 対応。`GalleryIndex` の再構築と `ArchiveStore` の保管記録を活用する。端末の選択・順位・編集状態を、B2側のキーから再生成しない。既存写真の `ArchiveStore.key` と画面側の識別子は切替時も維持する。新しい永続IDとの対応は転送前に保管記録へ保存し、再試行でも再利用する。対応が曖昧な場合は保留し、別写真へ設定を付け替えない。

## B3 機種変更後に保管済み写真を復元する

- 機能・要件。新しい端末でB2に接続し、原本全体を取り直さずに保管済み写真の一覧を復元する。旧端末を失っても、B2へ保存済みのカタログから再開できる。
- 方式案。SQLiteのDBファイルを直接コピーする代わりに、整合した保管記録を版付きの圧縮カタログとして書き出す。写真ID、原本のキー・版・サイズ・SHA-256、名前、フォルダ、撮影日時、機種、向き、プレビュー参照を含める。認証情報、端末URI、キャッシュは含めない。タグ・順位・編集設定の機種変更対応は別の契約とする。
- 保存契約。カタログの世代・件数・書式版と内容のハッシュを記録し、世代ごとの変更されないオブジェクトとしてB2の専用接頭辞へ保存する。保存と読み戻しが成功した世代を復元点とする。最新候補が不完全なら、前の有効世代から復元できる。破損を空のカタログとして扱わない。保存頻度と世代の保持数は実測に基づいて決める。
- 復元契約。専用接頭辞のカタログ候補だけを列挙する。最新から順に、バケットとライブラリの識別子、書式、件数、ハッシュ、IDの一意性、キーとサイズの制約を確認する。サイズ上限を設けて展開し、一時領域で検査してからSQLiteに反映する。既存データとの衝突があれば保留する。復元直後の記録は閲覧と原本取得に使い、端末原本の削除許可には流用しない。
- 利用者に見える結果。写真情報を先に取り込み、プレビューは順次取得する。原本は編集・共有等で必要になったときに読み込む。復元できる範囲は最後に公開したカタログまで。直後の保管分を無条件に復元できるとは扱わない。
- 端末切替。初期段階は1台だけが書き込む。新端末の初回復元は読み取りとして扱う。旧端末が利用できる場合は同期を停止し、最新カタログの保存を確認する。旧端末がない場合はB2側で旧端末の書き込みキーを失効させ、最後の有効なカタログから復元する。どちらの場合も旧キーの失効を確認し、新端末専用のキーを設定してから書き込みを再開する。世代の競合が見つかれば書き込みを保留する。複数端末の同時更新はD1同期を設計する際に扱う。

## B4 端末原本とAmazon原本を保全しながら移す

- 機能・要件。B2での保存・復元を検証してから、新規保存と既存分の移行を段階的に切り替える。未確認の写真を失わず、停止地点から再開できる。
- 不変条件。初期試行では端末原本を保持する。Amazon側の原本を移行処理で削除しない。既存の保管先を一括置換せず、確認済みの写真だけB2参照を追加する。保存先を切り替えた後の失敗で、別サービスへ自動送信しない。
- 端末容量整理の前提。後続実装で有効化するには、P6の原本再取得・照合、永続プレビュー、利用者設定と権限の条件に加え、該当原本が検証済みカタログの復元点に含まれることを要求する。照合済みでもカタログ公開前は端末原本を残す。端末の原本内容と権限を削除直前に再確認する。

| 順序 | 確認してから進む条件 |
| --- | --- |
| 1. B2への接続試行 | 少量のRAW/JPEGで原本・プレビュー・カタログを保存し、別環境で復元できる |
| 2. 新規保存の切り替え | 新規分がB2へ保管され、Amazon分は既存の参照で閲覧・取得できる |
| 3. 既存原本の移行 | HDDへ取り出した原本を移行台帳で管理し、SHA-256照合とカタログ保存が完了した写真だけB2を復元先に加える |
| 4. Amazon依存の取り外し | 対象・成功・保留件数を照合し、旧端末なしの復元で一覧と原本を確認する。保留写真があれば依存解消を完了としない |

既存の `ArchiveStore` にSHA-256がある写真は、HDDの原本と照合する。記録のないAmazon原本は、取り出せたバイト列のSHA-256を新しい照合元とし、古い端末原本との一致までは主張しない。同名や同時刻だけで既存写真に結び付けない。同じ端末上での移行後も既存の順位・タグ・編集情報が同じ写真に対応することを確認する。移行台帳には取得元識別子、内容ハッシュ、処理結果を残し、再実行で確認済みの転送を繰り返さない。原本の取得経路と対象範囲は少量で先に検証する。約856GBの全量移行は別工程とする。

## 実装前に確認する条件

| 確認 | 合格の根拠 |
| --- | --- |
| B1の接続・保全 | 試験用B2で最小権限キーを使い、RAW/JPEGのサイズ・SHA-256の一致を確認。認証切れ、応答喪失、同名別内容、アプリ再起動で再試行しても原本を誤登録しない |
| B2の表示 | 数万枚の合成カタログで、端末に索引がある状態の起動から最初の写真描画までを計測。オフラインで既存一覧を開け、起動・一覧操作でB2全件列挙が発生しない |
| B3の機種変更 | 旧端末のアプリデータを持たない環境でカタログを取得し、件数・写真ID・表示順・選んだ原本のSHA-256を照合。途中停止、破損・未対応版・別バケット、前世代への復帰、旧端末がない状態でのキー失効と新規保存も確認 |
| B4の移行と整理 | 少量の実原本で台帳と復元を照合。未照合・未公開・権限不足・端末原本変更時に削除されないことを確認。全量移行後に対象と保留を再集計 |

計測では端末・アプリ版・ネットワーク・枚数・形式・キャッシュ状態を記録する。初回復元は開始から最初の一覧表示、最初のプレビュー描画、全カタログ反映までを別々に測る。原本取得は操作から取得・ハッシュ検証・表示または共有準備完了までを測る。秒数、転送バイト数、再試行回数を残し、実測後に許容値とカタログ保存頻度を決める。[診断ログ](diagnostics.md)。

B2の実アカウント・リージョン、アプリキーの必要権限とSDK、Amazonからの原本取得経路、カタログ容量・保存間隔・世代保持、既存タグや編集設定の移行範囲は未確定。今回の確認は設計と現行コード・公式仕様の照合まで。実装・実データ移行・実機計測は後続工程で行う。
