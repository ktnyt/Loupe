# SD card re-detection before Android card-to-card import

## Purpose and scope

Import original photos from a source SD card to the selected microSD card in the same USB reader when Android retains stale media state after a card swap. Re-detect the reader before using the existing mounted-source importer. Source originals remain read-only. Re-detection does not copy photos or select a different destination.

This contract extends [card-to-card import](dual-slot-import-contract.md), [source swap](sd-source-swap-contract.md), [listing](sd-reinsert-listing-contract.md), and [Material 3 UI](material3-ui.md). It replaces the assumption that Android already observes every card change; original-byte reads, SHA verification, durable receipts, cancellation, and destination identity requirements remain authoritative.

## Requirements

1. Offer an explicit re-detection action on the import screen. Use public Android USB APIs without Shizuku, shell commands, hidden APIs, USB resets, or raw filesystem writes.
2. Re-detection reserves admission before opening Android Settings and remains exclusive with import and photo movement, including accepted, queued and automatically started operations. The prerequisite admission contract is [camera operation admission](camera-operation-admission.md) (#260). A running import must never be interrupted to re-detect a card.
3. Enable force claim only on the allowlisted, physically validated stock Xiaomi 15 firmware and Anker A83D1 reader configuration. The user must identify both inserted cards as ordinary single-partition portable camera/storage cards, not Android internal/adopted storage. Reject unexpected emulated/nonremovable layouts, null/duplicate UUIDs, extra devices or uncertain card use; offer safe physical reconnection instead. Public enumeration does not prove hidden adopted partitions absent. Force-claiming a mounted writable volume is forbidden. Capture the exact reader connection and unique UUIDs of all visible removable volumes while the selected destination is mounted. After a user-initiated Android settings flow, require the same entries positively unmounted and an explicit confirmation that Android reported every displayed card safe to remove, the reader stayed connected, and no formatting or mounting is in progress. Public MEDIA_UNMOUNTED also represents formatting and is never sufficient authorization by itself. A missing volume, failed query, denied permission, unknown topology, checking state, or read-only mount is not evidence of safe ejection. The app cannot silently eject volumes using a SAF tree grant: root ejection requires a different URI permission.
4. When safe ejection is needed, explain that both cards must be safely removed in Android while remaining physically connected. Open Android storage settings. On returning, re-read actual states; returning from settings or dismissing the dialog does not authorize the claim. Authorize only a single explicit confirmation in the same live short-lived settings attempt. Cold entry, rotation, a disappeared previously visible volume, extras/duplicate UUIDs, stale USB callbacks, timeout and cancellation invalidate it. Request USB permission before the final confirmation; revalidate after the OS permission flow.
5. Bind an attempt to the same selected destination, exact USB device connection, and intended source. Re-check before claiming and after restoring Android access. A connection, target or inventory change before claim, extra reader, permission loss, cancellation, or unknown safety state fails closed. After recovery, discover the actually mounted source under the ordinary source authorization rules.
6. Request Android USB permission only from a foreground user flow. Claim the single supported mass-storage interface, release it, and close the connection in finally. Send no storage data or SCSI commands. Claim/release success alone is not recovery success.
7. Wait for Android to remount the same destination and a distinct source. Check destination writability and rediscover current source/grants. A source absent before recovery has unknown identity; discover it afresh instead of assuming the old source returned. A currently mounted source with an existing valid DCIM registration, persistent read grant and distinct writable destination may reuse its authorization even when its UUID differs from the initial source. New, revoked, ambiguous and legacy volume-root registrations require the existing picker; never reuse another card's listing or automatically change the saved destination. Bound the wait, expose failure/retry, and do not spin/reclaim repeatedly.
8. Discard mount-triggered import admissions during preparation, USB handoff, cleanup and remount reconciliation; do not queue or replay them. After the reservation ends, subsequently delivered Android mount notifications follow the existing `sd_auto` path and its current-source/destination/generation/grant checks. This may include a delayed notification caused by re-detection. The re-detection controller never directly starts a copy. Preserve the existing automatic JPEG+RAW default; it is not a promise to enforce manual per-card kind preferences. Do not retain a reader-wide suppression latch or force a registered current source to be picked again using transient UI state.
9. Observe public media/storage and USB events and re-check on resume. When a card-change event is observed, invalidate stale listing/generation and perform read-only rediscovery. Expose the re-detection/preparation action if needed. Events never authorize or automatically perform a force claim, because public unmounted state cannot distinguish formatting from safely ejected media. An OS that reports neither an event nor a changed state cannot be assumed to have detected a physical card swap; do not periodically detach a mounted reader to guess.
10. Preserve camera/MTP import, internal-storage USB reads, legacy history and existing photos. Remove only code made unreachable by this implementation, with reference checks. Do not restore the closed raw-write or Shizuku implementation.

## UI and lifecycle

On the supported Xiaomi firmware, the public storage-settings action opens the Settings task. The verified safe-ejection path is Settings → About phone → Storage → scroll down → USB drive → Unmount USB device. The app guidance must make that path findable and distinguish unmount from the adjacent format action. Opening this screen alone never proves ejection.

The import screen retains its existing structure. Add a Material button for re-detection and a compact state message/progress indicator. Distinguish safely ejecting cards, waiting for USB permission, re-detecting, waiting for Android, source selection required, ready, busy and failed states with text and accessibility names, not color alone. Settings guidance uses a Material dialog with explicit open-settings and cancel actions. No automatic claim follows a canceled or abandoned user flow. Rotation/back/stop/destroy must not leak receivers, retain an Activity from background work, authorize a stale USB permission callback, or start a second attempt. Always attempt release and close after a claim attempt even if the view is gone or claim reports false: force claim may detach the driver before failing. A failed attempt offers safe manual reconnection and never automatically retries. Preserve chosen destination and provide explicit retry after failure.

## Acceptance and evidence

- Host tests cover safe/unsafe/unknown volume states, exact USB identity and target, contention, cancellation and errors at every USB step, cleanup, timeout, own-event suppression, duplicate events, lifecycle cancellation and changed/ungranted source.
- Synthetic Android checks cover supported/unsupported/busy/ejection-needed/permission-denied/waiting/timeout/ready states and settings return without side effects. Capture 400dp/font1.0 and 320dp/font1.3 with an independent UI review.
- Physical checks wait until the user's current transfer has ended. Use a separate test application or the documented recovery gate. Confirm Android's system-UI safe-ejection states and public-API claim/release/remount without ADB unmount or Shizuku. Confirm source/destination identities and keep existing originals. Transfer a bounded approved fixture and read back destination bytes before claiming production transfer is verified.
- Exercise physical source-card change if the user is available to swap it; otherwise mark actual insertion/removal and unattended reliability unverified. Never claim a synthetic broadcast proves hardware detection.
- Review independently for correctness and security. Merge through normal CI and deliver a clean-main APK through the existing deployment gate. Installation, readback and remaining physical checks are separate from implementation completion.

## API evidence

- [USB exclusive claim and release](https://developer.android.com/reference/android/hardware/usb/UsbDeviceConnection).
- [Android 16 DocumentsProvider root-URI ejection permission](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-16.0.0_r1/core/java/android/provider/DocumentsProvider.java).
- [Storage volume callback](https://developer.android.com/reference/android/os/storage/StorageManager.StorageVolumeCallback).

- [Android 16 public storage-state mapping, including formatting](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-16.0.0_r1/core/java/android/os/storage/VolumeInfo.java).

The public inventory restriction is a bounded supported configuration and user prerequisite, not a claim that ordinary apps can map every hidden volume to a USB interface. Xiaomi 15 has no internal microSD slot ([manufacturer FAQ](https://www.mi.com/global/support/faq/details/KA-541720/)); other devices and unvalidated firmware use safe physical reconnection.
