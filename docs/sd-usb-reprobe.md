# Foreground SD card refresh

On the supported phone and USB reader, Android can retain the previous SD card's volume information after a card swap. Loupe refreshes the reader from an explicit import action and uses the newly mounted source for the existing card-to-card import. The chosen external destination and the existing source registrations stay in place. Original photos stay on the source card.

## Import actions

- Opening the import screen from the library tab or gallery menu refreshes the reader once and shows the current source status. Opening the screen does not start a copy or open the folder picker.
- Long-pressing the library import tab refreshes once before continuing keep-originals quick import. An actionable registered source follows the existing import flow. A newly mounted source without a usable registration opens Android's normal folder picker.
- 「SDカードを再認識」 is an explicit retry. It refreshes the displayed source state without starting a copy.
- USB attach, mount events, resume, activity recreation, progress links, and automatic import do not start a refresh. Android USB permission can complete the same outstanding request in the foreground once. Unsupported phone, reader, storage layout or camera routes keep their ordinary import behavior.

## USB and storage contract

- Use the exact allowlisted Xiaomi 15 firmware and Anker A83D1 configuration, a single connected reader, and an external destination selected in Loupe. Both cards must use portable storage with one partition per card. Public Android storage inventory cannot identify hidden adopted partitions. Require the expected primary storage and at most two distinct removable volumes. The selected target must be mounted writable and a visible source must be mounted readable at admission. The source may be absent from the initial inventory. Ambiguous, transitional and unexpected layouts do not authorize a claim.
- Reserve [camera transfer admission](camera-operation-admission.md) before requesting USB permission. An accepted, queued, or running camera import or photo move prevents a refresh. Keep the reservation while permission is outstanding and transfer it to the worker. The worker obtains the shared I/O lock. Recheck the foreground authorization, reader, selected destination, volume inventory, and mount generation before the single claim. Leaving the screen or changing reader or destination invalidates the request. A stopped permission flow releases admission and ignores its late callback.
- Claim the one supported mass-storage interface using Android's public USB API. Mounted portable cards are eligible for this user-initiated refresh. After a claim attempt, attempt release and close the connection, including on errors or cancellation. Send no storage commands and write no data in order to check readiness.
- Discard the old source display and any outstanding source scan. After release, inspect the current Android volume inventory and wait up to 12 seconds for the selected target and a distinct readable source. A changed UUID can identify a new source. An unchanged UUID requires an observed loss of the old source during the handoff. Android must report that source unreadable or return a valid inventory containing only the mounted target. A detach notification alone does not confirm the source disappeared.
- Confirm the selected destination is writable and check the actual mounted source's existing DCIM registration and read grant. Continue only with the same reader and destination. Unknown, revoked, ambiguous and legacy volume-root registrations require the normal picker. Failure offers a fresh manual retry or safe physical reconnection. It never starts import.
- The admission reservation blocks imports during permission, handoff, cleanup and remount reconciliation. After verified restoration, automatic SD import ignores delayed broadcasts for the restored source cycle. A later detach plus an inventory confirming that the source is unavailable ends attribution, even when the detach does not identify a UUID. A different mounted source can use the existing automatic path. After an attempted claim ends without verified restoration, automatic SD import stays paused for that reader and destination in the current process. Android provides no way to distinguish a late remount caused by the handoff from a later physical reinsertion with the same evidence. Use a new explicit import action or reconnect the reader after safe removal. A positively observed reader or destination change ends attribution. If Android temporarily cannot report the connection, permission or storage inventory, Loupe retains attribution and suppresses matching automatic import requests until it can check again. An incomplete observation cannot authorize a new USB claim. Loupe leaves the automatic import setting as configured.

## UI and verification

The existing Material 3 import layout exposes a retry button, accessible state text, and an indeterminate indicator. Refresh replaces the previous source status and temporarily disables import actions. USB permission, remount wait, selection required and failure each have a textual status. Back, stop, and rotation cancel the outstanding attempt or stop its wait. Android never starts a second handoff during restoration.

Host tests cover mounted admission, topology, exclusivity, lifecycle authorization, replacement reader and destination, cleanup, timeout, source replacement, and delayed own-mount notification attribution. The camera-pilot-sd-usb-reprobe instrumentation mode exercises synthetic explicit open, long press, retry, permission and cancellation on a dedicated emulator at 400dp/font 1.0 and 320dp/font 1.3. A separate physical check verifies Android USB permission, mounted claim/release, observed source and destination identities, and any approved copy and readback. Synthetic data does not exercise the real reader or USB stack.
