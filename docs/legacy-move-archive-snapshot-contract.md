# 旧取り込み写真の移動中にE2記録が更新された場合の照合

## 目的と適用範囲

別の写真のバックアップ更新に妨げられず、証拠を確認できた写真をSDカードへ移動できるようにする。旧取り込み写真の候補抽出、事前確認、移動と再開で使う `LegacyArchiveMoveProof.Records.read` を対象とする。移動を許可する条件は[旧取り込み写真の移動前確認](legacy-time-move-contract.md)に従う。

E2台帳の `index_revision` は、どの写真への書き込みでも進む。現行の読み取りでは、全件走査の前後でこの値が異なると空の結果を返す。有効な証拠があっても照合に失敗し得る。常用端末で停止したときの理由は記録されておらず、この競合が当時起きたかは未確認である。

## 読み取りと再試行

1. 読み取り専用で開いた同じデータベースを使い、端末番号、inode、整数型の非負のリビジョンを調べる。キャッシュを使えるのは、この3つが前回の成功時と一致する場合に限る。中断要求はキャッシュを使う前にも確認する。
2. キャッシュを使えないときは、既存の走査で全状態の行を調べる。最後にファイルの同一性とリビジョンを再確認する。前後が一致したときだけ結果と対応するリビジョンを組にして保存し、呼び出し元に渡す。照合時点はこの最後の確認であり、以後の確認箇所でもその時点の台帳を読む。
3. ファイルは同一で、正常に読み取ったリビジョンだけが変わった場合は、走査結果を捨て、最新のリビジョンを取得して先頭から読み直す。1回の呼び出しにつき最初の走査を含めて最大3回とし、3回とも変わった場合は照合不能として扱う。途中の結果、以前のキャッシュ、最後に読んだ1行で移動を許可しない。
4. ファイルの差し替え、リビジョンの欠落や型不正、DBのオープン・読み取り失敗、JSONをオブジェクトとして読めない行、1走査10万行の上限超過は、その場で照合不能とする。中断は各走査の前と走査中に確認し、`InterruptedIOException` を呼び出し元へ返す。いずれもキャッシュを更新しない。件数上限までの正常な空の結果と読み取り失敗を内部で区別する。
5. 各走査で、対象のURIを持つ全状態の行を数える。唯一の行が厳密な形式の検証済み記録であり、履歴、写真のメタデータ、MediaStoreの現在のバージョン、世代範囲から再構成したキー、保存済み証拠が一致する場合だけ照合に成功する。別の写真の正常な更新は許容するが、同じURIに追加された未検証の行、証拠の削除や変更も、安定した読み直しで判定する。

Androidの最小対応版はAPI 30である。ここでは読み取り専用接続と既存のリビジョン検査だけを使う。読み取り専用トランザクション用の新しいAPI、書き込み予約を伴うトランザクション、WAL設定の変更、E2転送全体との排他は用いない。Androidのカーソルはウィンドウを補充することがあるため、カーソルを開いた時点だけで全行の一貫性を判断しない。写真数にかかわらず、ファイル入出力やMediaStoreの操作をまたいでDBのカーソルを保持しない。

## 移動の条件と停止時の診断

再確認箇所、候補検索とキー再構成の予算、選んだ履歴とカメラ台帳の照合、原本のSHA-256、移動先のURI・バージョン・追加世代への紐付け、状態に応じた更新世代・メタデータ検査を維持する。元の写真を削除する直前にも既存の再照合を行う。既存の作業記録からの再開では、同じ履歴、原本、移動先だけを使う。

読み取り結果には成功か失敗かと固定の理由を持たせる。候補一覧・事前確認は従来どおり未確認の候補を除外できる。移動中の照合で処理を止めるときは、その判定の理由を上位に渡す。利用者に表示する既存のメッセージと、書き込み済みの再開位置を保つ。

| 判定箇所 | 区別する理由 |
| --- | --- |
| E2台帳を読む | `archive_open`、`archive_read`、`archive_file_changed`、`archive_revision_invalid`、`archive_revision_churn`、`archive_write_busy`、`archive_json_invalid`、`archive_row_limit` |
| 対象URIの証拠を調べる | `receipt_missing`、`receipt_duplicate`、`receipt_unverified`、`receipt_invalid`、`receipt_metadata` |
| 証拠を作り直す | `history_metadata`、`epoch`、`generation_range`、`proof_budget`、`archive_key`、`saved_proof` |
| 移動中の他の照合 | 元の判定に対応する固定値で、履歴・台帳の競合、原本・別名の同一性、確定済み証拠、SHA-256、移動先の識別・メタデータを区別する。 |

同じURIの件数を先に判定し、唯一の行が検証済みか、形式が正しいか、その内容が写真と一致するかを順に判定する。理由は実際に失敗した検査で決める。判定をもう一度実行してログの理由を推定しない。日常利用版でも、移動が止まった際に専用タグの `Log.w` に理由、作業段階、走査の試行回数だけを1行出す。走査していない場合はその旨が分かる値を使う。例外本文、スタックトレース、ファイル名、URI、バケット、キー、ハッシュ、履歴IDは含めない。件数の多い候補一覧では、候補ごとの警告を出さない。現在の常用APKは `assembleDebug` で作るため、既存の `DiagnosticLog` も利用できる。ログ全体の設定や保存期間は変更しない。再開前にタグを指定してログの取得を始めれば、停止時の行を収集できる。

## 実装後の受け入れ条件

`LegacyArchiveMoveProof.java` が台帳の読み取りと証拠照合を担い、`PhotoMove.java` が作業段階と終了理由を結び付ける。検査は `LegacyArchiveMoveChecks.java` の既存の合成データとSD付きの専用エミュレータ（`jp.nano.rawgallery.sd162`）を使う。

- 競合を再現する位置は、実際の全件走査でカーソルを閉じた後、終了リビジョンを読む前とする。テストから別接続の書き込みを確定できるようにし、待ち時間やスレッドの偶然の順序に依存させない。先に安定時の証拠を確定し、キャッシュミスとなる新しい読み取りで競合を起こす。旧判定が証拠を捨てる条件を確かめ、最初の2回に別々の無関係な更新があっても3回目に同じ証拠を返し、合成写真の移動を完了できることを確かめる。
- 同じ位置で、対象の行の削除、SHAの変更、未検証化、別キーによる同じURIの追加をそれぞれ確定すると、最新の安定した走査で拒否する。追加行の状態は検証済み、保留、解放済みの各場合を含める。元の写真と履歴を保持し、拒否した作業段階から進まない。移動先がすでに公開済みの再開でも同じ条件で確認する。
- 毎回別の書き込みを確定すると3回で停止し、理由は `archive_revision_churn` となる。書き込みが止まった次の呼び出しで新しい状態を読み直す。別の試行では、成功してキャッシュを作った直後に対象の行を変更し、同じ読み取りオブジェクトで変更を検知することを確認する。
- 中断、DB未作成、リビジョン不正、壊れたJSON、件数上限の超過を区別し、途中の走査が証拠として残らないことを確かめる。実際の停止処理で、証拠の欠落とメタデータ不一致が競合とは別の理由になること、ログに固定値と試行回数だけが出ることを確認する。
- 通常のキャッシュヒットに全件走査が増えず、安定したキャッシュミスは1回、競合時は最大3回の走査で終わることを確認する。実機に近い12,478行の合成台帳で、別の写真への書き込みを500、1000、2000ミリ秒間隔で続ける。各条件で複数回の再照合を含む合成写真の移動を最後まで実行し、別接続で実際に確定した書き込み回数、走査・再試行回数、所要時間を記録する。この間隔は試験条件であり、常用端末で測った値ではない。書き込みと読み取りの重なりを観測できなければ、競合下の合格とはしない。既存の事前確認、移動先の差し替え拒否と再開の検査も通す。常用端末での停止原因や改善の有無は、実際の再開時の結果と区別して報告する。

## 継続的な更新で停止する場合

まず、既存のリビジョン検査で最大3回読み直す方式を測る。この方式は安定した1回の走査を必要とする。上記の頻度で通常のE2更新が続くと合成写真を移動できない場合、この方式だけでは受け入れ条件を満たさない。

その場合は、最後の1回の走査だけを、同一プロセスのE2台帳への書き込みと排他にする。対象は `ArchiveStore.put` でE2の `photos` に1行を書き込む期間と、読み直す側の先頭リビジョン取得から終了リビジョン確認までに限る。別名の台帳、ネットワーク転送、写真の入出力には広げない。書き手はDBを開いて値を準備してから排他区間に入り、読み手は区間内で他のアプリ内ロックを取らない。読み手の取得待ちは最大2秒とし、50msごとに中断を確認する。取得できなければ `archive_write_busy` と実行済みの走査回数を返す。中断・例外でも必ず解放し、ログ収集や待ち合わせを区間内で行わない。別プロセスや直接SQLからの更新に備え、最後の走査でも前後のリビジョンを確認する。この方式を採用した場合は、通常の書き手が走査後に進み、直接SQLで走査の前後に割り込んだ場合は照合を拒否することも検査する。元の写真を残すための判定を緩めて試験を通さない。
